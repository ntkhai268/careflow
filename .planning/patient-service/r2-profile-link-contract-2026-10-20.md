# R2 — ownership and reception contract

Implemented and deployed to the owned local test stack; API/PostgreSQL/web evidence is in ../appointment-service/r2-acceptance-2026-10-20.md. Physical native consent/camera/GPS acceptance remains open; no production acceptance is claimed.

Patient owns current profile ownership. Appointment/Queue ownership fields are historical snapshots and cannot authorize patients after a link/revocation. Current-owner reads must query Patient without cache. A narrow internal GET, authenticated with mTLS CN and an independent service credential, exposes only patientId/userId to Appointment, Queue, Consultation and Notification. It is outside Gateway routes. Failures deny reads and defer notification delivery, never fall back to stale ownership.

Linking is for the account holder only, with an Identity CONFIRMED in-person document check matching the reception profile's document/name/birth date. No representative grants and no merge of clinical records. Matching names/documents alone is insufficient: an authenticated owner creates a 5-minute random authorization, assigned receiving staff checks the original record and opens a request, and the authenticated owner explicitly approves the pending request. Only the hash of the authorization is stored; raw codes never enter URLs or audit records. Identity remains the document-verification authority and returns a matching check identifier, not document fields.

States: PENDING_OWNER -> LINKED / REJECTED / EXPIRED / DUPLICATE_REVIEW; LINKED -> REVOKED. One pending/live link per profile. A conflicting already-owned profile is a manual duplicate review, with no medical access granted. Rejection resolves review without merging. Revocation clears the owner, preserves clinical records and writes immutable audit. Existing user/card uniqueness stays; the old unique unowned-card index must be removed so revocation cannot fail because another reception profile has the same card. Reception creation still serializes and rejects duplicate unowned cards.

API under /api/patients/profile-links: owner authorization, owner request list, owner decision/revoke; staff proposal/review list/reject/revoke with current room assignment. Commands are idempotent with UUID request identifiers. No automatic consent/demo grants in seeding. Staff sees only administrative demographics and reference/status, never EMR through this workflow. Search uses POST body, rate limits and audit without raw query.

Integration order: Patient provider + Identity exact confirmed-match delegation scope, then current-owner clients, then web/native controls. Required private runtime settings: security.patient-owner.url and patient.internal-readers-json; preserve existing caller secrets. No Resend or external KYC changes.

Document matching uses NFC and case/whitespace normalization without removing accents or fuzzy matching; document number and birth date stay exact. New checks store the canonical HMAC. Legacy checks whose plaintext was already erased support bounded common case variants; other mismatches fail closed. Hash-only legacy rows cannot be generally re-normalized without a new authorized verification.
